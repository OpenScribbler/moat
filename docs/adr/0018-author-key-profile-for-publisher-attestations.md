# 0018. Author-Key Profile: SSHSIG publisher attestations trusted through a signed allowed-signers list

Date: 2026-10-24
Status: Accepted
Feature: author-key-profile

## Context

Keyless signing was the only normative publisher mechanism. For a Self-Publisher, whose source and registry are one repository, that makes the two Dual-Attested signatures come from two workflows in the same repository, so anyone with push access can produce both. The Self-Publisher case motivates a publisher attestation that push access alone cannot produce: a signature from a key the Publisher holds outside CI.

Three earlier records bound the design. v0.4.0 removed the v0.3 SSH signing profile when MOAT moved from per-item creator signing to registry-level trust. ADR-0008 made Rekor the authoritative store for publisher signatures, with the expected identity disclosed beside the content, and ADR-0011 (which supersedes it) made the client's path a single Rekor query keyed on the Content Hash and filtered by that identity, with no log-index locator.

Rekor constrains the encoding. A `hashedrekord` entry accepts only X.509 and PKIX keys, so an SSH signature must be a `rekord` entry with public-key format `ssh`, and Rekor's SSH verifier checks SSHSIG with namespace `file`, which fixes the namespace.

## Decision

Chose **the Author-Key Profile as the second attestation of the existing Dual-Attested tier: an OpenSSH SSHSIG (namespace `file`, hash `sha512`) by an `ssh-ed25519`, `sk-ssh-ed25519@openssh.com`, or `sk-ecdsa-sha2-nistp256@openssh.com` key over a message that begins with the domain separator line `moat-author-item-v1`; recorded in Rekor as a comment-free `rekord` entry; located by ADR-0011's query shape filtered by key fingerprint; trusted through `.moat/allowed_signers` in the source repository, a fingerprint-principal subset of OpenSSH's allowed-signers format, carried verbatim in `signing_profile`, confirmed by the End User on first sight, and changed silently only by a list-change signature (separator `moat-allowed-signers-change-v1`) from a key the previous list allows, over a message that binds the `source_uri` and a monotonic sequence the list itself carries, with a keyless `signing_profile` for a source whose list a client trusts handled as a first sight** over **a new trust tier for author-signed content; cosign with a self-managed key pair; minisign or signify; a bespoke Ed25519 envelope; per-item key lists; requiring FIDO attestation to prove hardware backing; every list change as a new first sight; a sequence carried only in the change message or in a separate file**.

## Consequences

**Tier model.** The registry still crawls, signs, and serves every item; the Author Key replaces only the CI workflow as the source of the publisher attestation. The v0.4.0 objection to SSH signing was that per-item creator keys acted as a trust root beside the registry. Here they do not: no item reaches a client without the registry's keyless signature, and an Author-Key signature can only raise a Signed item to Dual-Attested. Unlike the v0.3 profile, every signature is in Rekor, and the key list is versioned in the source repository and copied into the registry-signed manifest.

**Signature scheme and key format.** SSHSIG is what `ssh-keygen -Y sign` produces and what git uses for SSH commit signing, so publishers on Linux, macOS, and Windows can sign with tooling they already have. Stock OpenSSH on Linux handles all three key types. Apple's bundled OpenSSH is built without the built-in FIDO provider, so generating an `sk-` key on macOS needs a FIDO-enabled OpenSSH build such as Homebrew's; signing with plain `ssh-ed25519` works with the bundled tools. Windows' built-in OpenSSH supports `-Y sign` and reaches FIDO authenticators through Windows Hello. cosign with a self-managed key was rejected because it adds a tool and a key format publishers do not already hold, and its hardware-key path needs a PIV build. minisign and signify have no security-key support, and a bespoke envelope would need bespoke tooling on every platform. `reference/test_author_key.py` checks every vector against `ssh-keygen`.

**Hardware backing.** The profile does not claim it. An `sk-` key type and the user-presence flag show only that the signature went through a FIDO authenticator interface; software authenticators exist, and the profile carries no authenticator attestation. Verifying FIDO attestation would need vendor root metadata and would publish device-identifying data in a public log, so it was rejected for this version. The spec therefore makes `sk-` types a SHOULD, requires the user-presence flag on them, forbids clients from calling any key or item hardware-backed, and requires the first-sight prompt to say a key type does not prove hardware binding. `ssh-keygen -Y verify` does not check the user-presence flag, so the spec requires a verifier to check it itself.

**Domain separator.** Because Rekor fixes the SSHSIG namespace to `file`, the namespace cannot keep a MOAT signature from verifying as a signature over some other file the same key signed. Each signed message therefore begins with a versioned separator line, one for items and one for list changes, so a signature over one kind never verifies as the other or as a bare Attestation Payload. The strings are new rather than the v0.3 `MOAT-V1:` prefix, so no v0.3 signature can be replayed.

**List location and format.** The list lives at `.moat/allowed_signers` in the source repository so the Publisher controls it under version control, and the registry copies it verbatim into `signing_profile` so a client gets it inside the registry-signed manifest without fetching the source. Each key line is `<fingerprint> <keytype> <base64>`, and the list carries exactly one `# moat-sequence: <n>` line: the fingerprint is the principal, so `ssh-keygen -Y verify -f .moat/allowed_signers -I <fingerprint> -n file` works unchanged, and no email or other personal identifier enters the list or the Rekor entry. OpenSSH's options field (`namespaces=`, `valid-before=`, `cert-authority`) is excluded to keep parsing trivial and unambiguous. Per-item lists were rejected because one source has one set of authors.

**List changes.** A client records the trusted list and its sequence per `source_uri` in the lockfile. A list-change signature binds the `source_uri`, the new list's sequence, and the previous and new list digests, so a client that holds the previous list accepts the new one without a prompt and reports which keys were added and removed. Binding only the two digests would let a signature replay in two ways: an old change that added a key the Publisher later removed could be recommitted to restore that key, and a change signed for one repository could be served for another that trusts the same list. The `source_uri` closes the second. The sequence closes the first: a client refuses any list whose sequence is not greater than the one it recorded, before it checks a signature and without offering a first sight, since a legitimate change never lowers it.

The sequence lives in the list file itself, as a `# moat-sequence: <n>` line, for three reasons. The list digest covers it, so a change signature commits to it without a new field. The registry already copies the list verbatim into `signing_profile`, so a client learns the current sequence at first sight with no extra file or manifest field. A sequence carried only in the change message could not be learned at first sight, because a first-seen list may have no change signature beside it. The line is a comment to OpenSSH, so `ssh-keygen -Y verify -f .moat/allowed_signers` still reads the file; a non-comment line would break it. Treating every change as a first sight was rejected because routine key rotation would train End Users to approve prompts unread. A client that missed an intermediate list cannot chain and falls back to a first sight, which keeps the rule to one signature instead of a replayed history. A stolen trusted key can rewrite the list, and can set a sequence no later list can exceed, so the Publisher cannot recover through the list itself. Recovery is the End User removing the source's trusted list, which every client must allow and which the sequence refusal names; the next list is then a first sight. A registry revocation blocks the items the stolen key signed but does not reset the trusted list.

**Keyless downgrade.** An attacker with push access to a Self-Publisher's repository cannot sign with the Author Key, but can delete the list, switch `.moat/publisher.yml` to keyless, and run the keyless Publisher Action, which yields a valid keyless publisher attestation. A client that consulted the list only for key-fingerprint profiles would accept that item as Dual-Attested. A client that holds a trusted list for a `source_uri` therefore treats a keyless `signing_profile` for that source as a first sight, and on confirmation drops the recorded list. A manifest may not mix a keyless and a key-fingerprint profile for one `source_uri`. The same attacker could instead respell the `source_uri` in the registry configuration, for example with a trailing slash or a letter-case change the host resolves to the same repository; the respelled source has no trusted list. Rather than define a canonical URI form, the lockfile records each installed item's `source_uri` (`entries[].source_uri`), and an update whose `source_uri` differs from the recorded one is a first sight when the recorded source has a trusted list. Removing the publisher attestation altogether leaves the item at the Signed tier, which the client already shows as lower.

**Relation to ADR-0008 and ADR-0011.** Rekor stays authoritative and the client path keeps ADR-0011's single-query shape: query by the SHA-256 of the item message built from the recomputed Content Hash, filter by `signing_profile.key_fingerprint`, refuse on zero matches. `signing_profile` carries no log index, consistent with ADR-0011's rejection of a locator. The npm channel's `publisherSigning` block keeps only the keyless form; extending it is left to a later npm sub-spec revision.

**Open dependencies.** `rekord` is a Rekor v1 entry type; a Rekor deployment that accepts only `hashedrekord` and DSSE entries cannot record these signatures, and the profile will need a new encoding before public Rekor drops v1 entry types. Whether Rekor's SSH verifier accepts `sk-` signatures is not yet confirmed against the public instance. `moat-verify` and the reference workflows do not implement the profile in this version.
